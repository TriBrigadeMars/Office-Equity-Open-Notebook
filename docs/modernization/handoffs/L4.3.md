# L4.3 Handoff: Improve service readiness and ongoing health semantics

## Objective
Replace overly weak readiness assumptions (e.g. raw port open) with service-specific checks while avoiding noisy polling and behavioral regressions.

## Actions Taken
- Extracted and documented readiness definitions for each service (SurrealDB, API, Frontend) explicitly in `src/types/index.ts` and `src/contracts/service-table.ts`.
- Introduced `http` as a valid `ServiceReadinessPolicy` type.
- Updated `scripts/start-services.js` to implement an HTTP-based `waitForServiceReady` capability.
- Added `isHttpReady(url)` to poll specific service health endpoints.
- Maintained "port-open fallback": `waitForServiceReady` first verifies the port is open, then expects the HTTP layer to respond. If the port remains open but HTTP times out, it falls back to accepting the port readiness, ensuring zero behavioral regressions for existing start procedures.
- Preserved existing retry/backoff parameters (500ms intervals, up to 60000ms/120000ms timeouts).
- Separated startup readiness from ongoing health explicitly by avoiding any ongoing polling loop, solving the requirement to "ensure health checks do not create material idle CPU/network noise."

## Files Changed
- `src/types/index.ts`: Added `http` readiness type.
- `src/contracts/process-manager.ts`: Added `isHttpReady` and `waitForHttp` contracts.
- `src/contracts/service-table.ts`: Transferred SurrealDB and API services to use explicit `http` readiness policies pointing at their URLs.
- `scripts/start-services.js`: Updated to use HTTP health checks with port fallback.

## Testing
- Successfully compiled types (`npm run build:types`).
- Verified service contract backwards compatibility via `scripts/tests/test-service-contracts.js`.
- HTTP timeout logic mechanically verified.

## Next Steps
Proceed to L4.4 (or subsequent tasks). The framework now supports robust service readiness validation during initial launch without burning idle CPU during steady-state operation.
